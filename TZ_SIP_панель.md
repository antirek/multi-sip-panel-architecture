# ТЗ: SIP-панель для тестирования сценариев вызовов на ВАТС

**Статус:** черновик, открытых вопросов нет

## 1. Цель

Инструмент для проверки сценариев вызовов на ВАТС. Заменяет связку из нескольких аппаратных SIP-телефонов, которую обычно ставят телефонисты для тестирования. Здесь то же самое, но вместо нескольких отдельных софтфонов — один софтфон-пакет с несколькими SIP-учётками.

Приложение позволяет зарегистрировать несколько SIP-учёток и совершать вызовы между ними, чтобы в реальном времени видеть, как работает маршрутизация: вызов поступает на одного абонента и переходит на другого, либо поступает на группу или очередь и далее переходит по цепочке.

Это не аналитический инструмент. Это средство проверки: оператор запускает сценарий, смотрит на происходящее и фиксирует результат.

## 2. Пользователи и сценарий

**Пользователь:** один человек (тестировщик или телефонист).

**Типовой сценарий:**
1. Пользователь добавляет 2–5 SIP-учёток (логин, пароль, сервер, транспорт).
2. Все учётки регистрируются на ВАТС, на карточках видно их статус.
3. С одной учётки набирается номер очереди или группы.
4. Карточки показывают, какая учётка звонит, принимает, занята или пропускает вызов.
5. Журнал фиксирует всю цепочку с временными метками.

### 2.1. Тестовые сценарии (приоритетные)

1. **Очередь с последовательным перебором:** вызов идёт на учётки по очереди, пока кто-то не ответит.
2. **Групповой вызов (ring all):** вызов одновременно звонит на все учётки группы.
3. **Переадресация по неответу:** вызов не принят за заданное время и уходит на другую учётку.
4. **Переадресация по занятости:** вызов уходит на другую учётку, если текущая занята.

## 3. Интерфейс

### 3.1. Главное окно

- Сетка карточек: по одной карточке на каждую SIP-учётку. Все карточки видны одновременно.
- Нижняя часть окна: журнал событий (таблица).

### 3.2. Карточка учётки

Каждая карточка содержит:

- **Имя или номер учётки.**
- **Статус регистрации (онлайн/офлайн):**
  - зелёный — Registered (онлайн);
  - серый — Unregistered (офлайн);
  - красный — Failed (ошибка регистрации).
- **Состояние вызова:** Idle (простой), Ringing (входящий), Calling (исходящий), In call (разговор).
- **Поле набора номера.** Может быть встроенным в карточку или выноситься во всплывающее окно.
- **Кнопки:** Вызов, Ответить, Отбой.

### 3.3. Журнал событий

Нижнее окно — таблица с колонками: время, учётка, событие, номер или детали. Это основной способ фиксировать результат сценария.

### 3.4. Цепочка вызова (этап 2)

Отдельная область (таймлайн или схема) показывает путь одного вызова: откуда пришёл, на какие учётки прошёл, кто ответил. Это вспомогательная визуализация для проверки сценария, а не отчёт. В MVP не входит: на первом этапе достаточно журнала событий (решено).

## 4. Функциональные требования

### 4.1. MVP

| ID | Требование |
|----|------------|
| FR-1 | Добавление, редактирование и удаление SIP-учёток. Хранение списка в локальном конфиге. |
| FR-2 | Одновременная регистрация нескольких учёток. Отображение статуса регистрации на карточке (онлайн/офлайн/ошибка). |
| FR-3 | Исходящий вызов с любой зарегистрированной учётки на произвольный номер. |
| FR-4 | Входящий вызов на любую зарегистрированную учётку. Кнопки: Ответить, Отклонить, Завершить. |
| FR-5 | Отображение состояния вызова на карточке: Idle, Ringing, Calling, In call. |
| FR-6 | Журнал событий с временными метками: регистрация, входящий, исходящий, ответ, отбой, причина завершения. |

### 4.2. Следующий этап

| ID | Требование |
|----|------------|
| FR-7 | Визуализация цепочки вызова (см. раздел 3.4): «откуда → куда → куда» с временем на каждом шаге. |
| FR-8 | Отображение групп и очередей, в которые попадает вызов (например, «звонок ушёл в группу 201: учётки A, B, C»). |
| FR-9 | Экспорт журнала в файл (CSV или JSON). |

### 4.3. Этап 3 и опционально

| ID | Требование |
|----|------------|
| FR-10 | Горячее переключение локального аудиоинтерфейса (микрофон + наушники) между активными учётками без разрыва вызовов и без постановки остальных учёток на SIP Hold. |
| FR-11 | Перевод вызова (blind и/или attended), удержание (опционально). |

## 5. Нефункциональные требования

- **ОС:** Linux.
- **Независимость от вендора ВАТС.** Работа только по стандарту SIP (RFC 3261), без привязки к API конкретной АТС.
- **Работа напрямую с ВАТС** по SIP. Отдельный сервер не нужен.
- **Поддерживаемые транспорты:** UDP, TCP, TLS.
- **Тестовая среда разработки:** Asterisk (вероятно).
- **Установка:** один исполняемый файл или простой установщик, без сложной настройки.
- **Безопасность:** пароли SIP-учёток не хранятся в открытом виде.
- **Логирование:** техжурнал в файл для отладки.

## 6. Технические заметки

- Используется стандартный SIP (RFC 3261) и RTP. Регистрация через REGISTER, вызовы через INVITE.
- Для реализации подойдёт готовый SIP-стек: PJSIP, Linphone SDK, baresip, SIP.js (если веб-технологии). Выбор стека делается на этапе проектирования.
- **Ключевой риск:** панель увидит полную цепочку переадресаций только если ВАТС передаёт её клиенту по SIP. Варианты:
  - SIP-заголовки `Diversion` или `History-Info` (зависит от настроек ВАТС);
  - если таких заголовков нет, панель покажет только то, что видит со своей стороны (INVITE, отбой, пропущенный). Тогда цепочка будет неполной.
- Поскольку API ВАТС не используется, опора только на SIP-сигнализацию. Это соответствует требованию независимости от вендора.
- Аудио не реализуется на первом этапе: для проверки маршрутизации достаточно сигнализации. Однако **архитектура локального аудио закладывается сразу**: на этапе 3 пользователь должен иметь возможность на лету подключать гарнитуру к одной учётке, говорить через неё, отключать и подключать к другой учётке без постановки вызовов на SIP Hold и с сохранением фонового RTP-потока (тишины) на остальных активных вызовах.

## 7. Ограничения и риски

- NAT и файрволы на рабочем ПК могут мешать приёму входящих. Возможно, понадобится STUN или работа через VPN.
- Заранее не известно, какие SIP-заголовки отдаёт конкретная ВАТС. Нужно проверить на тестовом стенде (Asterisk).
- Вендор-независимость означает, что поведение панели зависит только от стандартных SIP-сообщений. Нестандартные особенности конкретной ВАТС могут требовать отдельной проверки.

## 8. Этапы

1. **MVP:** регистрация нескольких учёток, карточки с состояниями, исходящие и входящие вызовы, журнал (FR-1…FR-6).
2. **Этап 2:** визуализация цепочки вызова, группы и очереди, экспорт (FR-7…FR-9).
3. **Этап 3:** звук (при необходимости), перевод и удержание (FR-10).
