# Анализ архитектурных вариантов и медиадвижков для SIP-панели

Сравнение вариантов архитектуры с учётом требований из `TZ_SIP_панель.md` и **закладываемой заранее архитектуры локального аудио**.

Исходные вводные:
- **ОС:** Linux (PipeWire / PulseAudio / ALSA).
- **Масштаб:** 2–5 SIP-учёток одновременно на одном ПК.
- **Протокол в сторону ВАТС:** стандартный SIP (UDP / TCP / TLS) + RTP, без привязки к вендору.
- **Аудио (ключевое уточнение):** в MVP можно работать без гарнитуры, но архитектура должна сразу позволять **на лету подключать локальный аудиоинтерфейс (микрофон + наушники) к одной активной учётке, разговаривать, затем отключать его и переключать на другую учётку** без разрыва текущих вызовов.

---

## 0. Архитектура локального аудио: что нужно заложить сразу

Если на столе телефониста стоят 3 аппаратных телефона, он может снять трубку на Аппарате 1, положить её рядом на стол (не вешая и **не нажимая Hold**!), и взять трубку Аппарата 2, чтобы проверить слышимость с другой стороны. В программной панели с одной гарнитурой это означает наличие **локальной аудиоматрицы (коммутатора)**.

Три технические ловушки, которые отсеивают неподходящие стеки:

1. **Запрет на автоматический SIP Hold при переключении звука.**
   Многие клиентские телефоны и SDK при смене «активного» звонка автоматически отправляют первому вызову `re-INVITE` с `a=sendonly`/`inactive` (ставят на удержание). Если Учётка 1 позвонила через очередь на Учётку 2 внутри нашей же панели, постановка Учётки 1 на Hold включит музыку на удержании на ВАТС и сломает тест. Переключение гарнитуры должно быть **строго локальным** — без отправки SIP-сообщений.
2. **Генерация фонового RTP (тишины) на учётках без гарнитуры.**
   Даже если от активного вызова отключили микрофон и динамики (или в MVP звук вообще выключен), медиадвижок обязан:
   - продолжать отправлять в сторону ВАТС RTP-пакеты с тишиной (silence frames) каждые 20 мс;
   - вычитывать входящие RTP-пакеты в «пустой приёмник» (`null sink`).
   Иначе любая ВАТС (например, Asterisk с `rtptimeout=30`) принудительно оборвёт вызов из-за отсутствия медиапотока, а NAT закроет порт.
3. **Полезный бонус правильной матрицы — тестовый генератор в неактивную линию.**
   Если один человек тестирует звонок «Учётка 1 → Очередь → Учётка 2» с одной гарнитурой, он физически не может одновременно говорить в Учётку 1 и слушать Учётку 2 (иначе возникнет акустическая петля). Если матрица позволяет подать в линию Учётки 1 зацикленный WAV-файл или тон 440 Гц, а гарнитуру подключить к Учётке 2 — тестировщик сразу ушами проверит сквозное прохождение звука через ВАТС.

Целевая схема внутри приложения выглядит так:

```text
[Учётка 1 RTP] <---> [ Порт 1 ] \
[Учётка 2 RTP] <---> [ Порт 2 ]  +--> [ Локальная аудиоматрица ] <---> [ Микрофон / Наушники ]
[Учётка 3 RTP] <---> [ Порт 3 ] /            ^
                                             |
                                 [ Генератор тишины / тона / Null Sink ]
```

Ниже рассмотрены 9 архитектурных вариантов, разбитых на три класса.

## Класс А. Встраиваемые SIP-комбайны с готовой аудиоматрицей

### Вариант 1. Python + PySide6 (Qt) + PJSIP (`pjsua2`)

Один процесс. UI на Qt, внутри крутится PJSIP. В сердце медиаподсистемы PJSIP лежит готовая аудиоматрица — **`pjmedia_conf` (Conference Bridge)**.

- **Как работает переключение аудио:** каждый активный вызов (`AudioMedia`), физическая звуковая карта (`AudDevManager.getCaptureDevMedia()` / `getPlaybackDevMedia()`), генератор тона и WAV-плеер — это просто порты матрицы.
  - В MVP включается `setNullDev()` — PJSIP сам гоняет таймер и шлёт валидный пустой RTP во все активные вызовы.
  - На этапе с аудио переключение гарнитуры с Учётки 1 на Учётку 2 — это два вызова методов `stopTransmit()` и `startTransmit()` между портами матрицы за миллисекунды, **без SIP Hold и без пересогласования SDP**.
- **Сильные стороны:**
  - Идеальное попадание в задачу переключения аудио из коробки.
  - Полный SIP-стек (UDP, TCP, TLS, STUN/TURN, кодеки, эхоподавление).
  - Полный доступ к сырым SIP-пакетам и заголовкам (`Diversion`, `History-Info`).
  - Быстрая разработка UI на Python.
- **Слабые стороны:**
  - Нет официального готового `pip install pjsua2` — нужно один раз настроить сборку PJSIP с флагом `--enable-shared` и SWIG под Python (удобно завернуть в Dockerfile сборки).
  - Лицензия GPLv2.
  - Неосторожная работа с потоками Python/C++ может приводить к падению процесса.

### Вариант 2. C++ + Qt6 (или Rust + Tauri) + PJSIP

Та же архитектура на базе матрицы `pjmedia_conf`, но без Python/SWIG: либо классический C++ (`pjsua2` + Qt6), либо ядро на Rust/C++ вокруг PJSIP и фронтенд на Tauri.

- **Как работает переключение аудио:** аналогично Варианту 1 — нативная матрица `pjmedia_conf`.
- **Сильные стороны:**
  - Максимальная стабильность памяти и потоков, родной API `pjsua2` без SWIG-прослойки.
  - В связке **C++/Rust backend + Tauri Web UI** получаем одновременно железобетонный `pjmedia_conf` для аудио/SIP и современную веб-вёрстку для карточек и таймлайна.
  - Простая упаковка в один AppImage / deb.
- **Слабые стороны:**
  - Выше порог входа и дольше разработка бэкенд-части, чем на Python.
  - Лицензия GPLv2 у PJSIP.

---

### Вариант 3. Linphone SDK (`liblinphone` + движок `Mediastreamer2`) + UI (Python / C++)

Комбайн от Belledonne Communications. Под капотом — модульный графовый медиадвижок **Mediastreamer2** (по концепции близок к GStreamer). Есть готовые обёртки для C++ и Python.

- **Как работает переключение аудио:** позволяет менять звуковые карты (`Core.input_audio_device` / `output_audio_device`) даже во время звонка, но имеет важную особенность: `liblinphone` спроектирован вокруг концепции «один активный звонок в фокусе, остальные на SIP Hold (`pause`)».
- **Сильные стороны:**
  - Очень зрелый SIP/RTP стек, отличное качество звука и кодеков, поддержка TLS/SRTP.
  - Удобный объектный API для учёток и вызовов.
- **Слабые стороны:**
  - **Плохо подходит под два одновременных «снятых с трубки» вызова без Hold:** чтобы Учётка 1 и Учётка 2 одновременно держали активный RTP-поток без отправки `re-INVITE (sendonly)` на АТС, приходится либо объединять их в локальную конференцию (тогда их звук смешается!), либо обходить высокоуровневую логику `Core` на уровне графов `Mediastreamer2`.
  - Строгая лицензия GPLv3.

## Класс Б. Медиадвижки с SIP-плагинами (Sidecar-демон + UI)

В этой группе приложение состоит из двух частей: готовый медиадвижок в локальном фоновом процессе и лёгкий UI (например, на Tauri, Electron или Python/Qt), общающийся с движком по WebSocket/JSON.

### Вариант 4. Janus WebRTC Server + плагин `libjanus_sip` + Tauri / Electron (Web UI)

**Janus** — компактный медиадвижок на C с плагинной архитектурой. Его штатный плагин **`janus_sip`** построен на базе проверенного C-стека **Sofia-SIP**.

- **Как устроено:**
  - Локально рядом с UI запускается бинарник `janus` только с двумя плагинами: `transport_websockets` (на `127.0.0.1`) и `plugin_sip`.
  - Каждая карточка учётки в UI открывает отдельную сессию в `janus_sip`.
  - В сторону ВАТС `janus_sip` говорит на **настоящем классическом SIP (UDP / TCP / TLS, порт 5060)** и обычном RTP (G.711, Opus, G.722).
  - Между локальным Janus и окном приложения ходит локальный WebRTC (по `127.0.0.1`, без задержек и без внешнего STUN).
- **Как работает переключение аудио:**
  - Решается средствами **Web Audio API** и браузерного движка в 10 строк кода:
    - На приём: у каждой карточки свой тег `<audio>`. Переключение наушников на нужную учётку — просто `audioEl.muted = false` на выбранной карточке и `muted = true` на остальных (плюс `setSinkId()` позволяет выбрать конкретную USB-гарнитуру прямо из UI!).
    - На передачу: создаётся `AudioContext`, куда заведены микрофон и генератор тишины/тона. В `RTCPeerConnection` неактивных учёток подаётся поток тишины (поэтому Janus исправно шлёт RTP в сторону ВАТС!), а при клике «Подключить гарнитуру» через `RTCRtpSender.replaceTrack()` в выбранную учётку бесшовно переключается реальный микрофон — **никаких SIP re-INVITE на ВАТС не уходит**.
- **Сильные стороны:**
  - Полностью снимает главное ограничение веб-софтфонов: UI пишется на удобном веб-стеке (React/Vue/Svelte в Tauri), а в сеть смотрит честный Sofia-SIP (UDP/TCP/TLS).
  - В JSON-событиях `janus_sip` приходят статусы регистраций, коды отбоя и кастомные SIP-заголовки входящих вызовов (можно читать `Diversion` / `History-Info`).
  - Не нужно писать C/C++ код и собирать SWIG-биндинги — `janus` и `janus-plugins` есть в готовых пакетах большинства дистрибутивов Linux (Debian/Ubuntu/Fedora/Arch).
  - Падение или перезапуск медиадвижка изолированы от окна UI.
  - Лицензия GPLv3 (но так как это отдельный процесс, код самого UI не обязан быть под GPL при взаимодействии через стандартный сокет).
- **Слабые стороны:**
  - Двухпроцессная схема: при упаковке в единый AppImage нужно положить внутрь бинарник `janus` с его `.so`-плагинами и генерировать для него минимальный конфиг при старте.
  - Небольшой оверхед на локальное перекодирование Opus (WebRTC) ↔ PCMA/PCMU (SIP), хотя для 2–5 звонков на современном ПК это доли процента CPU.
  - В MVP «совсем без звука» всё равно нужно поднимать тихий/фиктивный `MediaStream` в скрытом WebView, чтобы Janus сформировал SDP и гнал RTP.

### Вариант 5. Локальный FreeSWITCH (`mod_sofia` + `mod_portaudio` / `mod_verto`) + любой UI по ESL

**FreeSWITCH** — профессиональный медиадвижок и софтсвитч, который имеет штатный режим работы как многолинейный клиентский телефон через модуль звуковой карты **`mod_portaudio`** (или WebRTC-модуль `mod_verto`) и SIP-модуль **`mod_sofia`**. Управление из UI идёт по TCP через **ESL (Event Socket Library)**.

- **Как устроено:**
  - Каждая SIP-учётка добавляется как SIP Gateway в `mod_sofia` (динамически через XML/ESL).
  - При входящем или исходящем звонке канал на стороне нашей панели ставится на парковку с генератором бесконечной тишины (`silence_stream://-1`) — ВАТС видит идеальный живой RTP.
- **Как работает переключение аудио:**
  - Звуковая карта открыта в `mod_portaudio`. Подключить гарнитуру к любой учётке — одна команда по ESL (`uuid_bridge` к каналу `portaudio` или `pa switch`), переключить на другую — перебриджевать на другой `uuid`. Никаких SIP Hold в сторону ВАТС, мгновенное переключение, плюс из коробки можно подать любой WAV/тон (`playback`) в любую линию.
- **Сильные стороны:**
  - Абсолютный максимум возможностей по SIP и медиа: полная трассировка SIP-пакетов, автоматический парсинг всех мыслимых заголовков (`variable_sip_h_Diversion` и т.д.) прямо в JSON-событиях ESL.
  - Лицензия MPL 1.1 (мягче GPL).
  - Безупречная работа с фоновым RTP, тонами, записью и аудиомаршрутизацией.
- **Слабые стороны:**
  - **Тяжеловесность:** FreeSWITCH — это большой серверный демон с десятками конфигурационных XML-файлов. Тащить его нативный бинарник внутрь портативного настольного приложения неудобно (вариант хорош, только если допустимо запускать движок в локальном Docker/Podman-контейнере или ставить системным пакетом).

### Вариант 6. `baresip` (фоновый демон) + маршрутизация в PipeWire / PulseAudio + UI

Модульный легковесный SIP-клиент на C (лицензия BSD) с управлением по JSON (`ctrl_tcp`).

- **Как работает переключение аудио:**
  - В `baresip` каждый параллельный звонок создаёт свой аудиопоток. На современном Linux (PipeWire / PulseAudio) каждый звонок виден как отдельный поток ввода/вывода (`Sink Input` / `Source Output`).
  - В MVP в конфиге учёток указывается модуль `ausine` / `aufile` / `null` (генерация тишины в RTP без звуковой карты).
  - Для переключения гарнитуры между вызовами UI управляет мьютом и привязкой потоков либо командами самого `baresip` (`/ausrc`, `/auplay` на лету для текущего вызова), либо напрямую через API **PipeWire / PulseAudio** (`pulsectl` в Python), глуша ненужные потоки и подключая микрофон только к выбранному вызову.
  - *Важный нюанс:* в `baresip` нужно отключить авто-удержание предыдущего вызова при ответе на новый (настройка `call_hold_other no` / управление через явные `call_find`), иначе сработает ловушка №1.
- **Сильные стороны:**
  - Очень лёгкий и быстрый демон (~1–2 МБ), лицензия BSD.
  - Родная интеграция с Linux PipeWire/PulseAudio.
- **Слабые стороны:**
  - Штатный JSON-интерфейс `ctrl_tcp` отдаёт не все произвольные SIP-заголовки (`Diversion` / `History-Info`) — для этапа 2 вероятно придётся дописать маленький C-плагин к `baresip` (~100 строк) или парсить его stdout SIP-трассировку.
  - Синхронизировать ID вызова в `baresip` с конкретным аудиопотоком в PulseAudio/PipeWire чуть хлопотнее, чем управлять единой матрицей внутри PJSIP или Janus.

### Примечание про серверные связки (Kamailio / OpenSIPS / Drachtio + `rtpengine`)
Иногда в качестве «медиадвижка с SIP» рассматривают `rtpengine` или `MediaProxy` в паре с SIP-прокси. Для нашей задачи они **не подходят**: это транзитные B2B/прокси-движки без клиентских звуковых драйверов (ALSA/PipeWire) и без полноценного состояния SIP User Agent (регистрации с digest-авторизацией и поддержание клиентских диалогов).

## Класс В. Конструкторы «Медиаконвейер + отдельный SIP-стек»

### Вариант 7. GStreamer (`rtpbin` + селекторы) + сигнальный SIP-стек (Rust / Python / Go)

Вместо телефонного комбайна берётся чистый мультимедийный фреймворк **GStreamer** для всего RTP и звука, а сигнализация (REGISTER, INVITE, парсинг SDP и заголовков) пишется на библиотеке вроде `sofia-sip`, `sipgo` (Go) или `rsipstack` (Rust).

- **Как работает переключение аудио:**
  - В GStreamer строится пайплайн с элементами `audiotestsrc wave=silence` (фоновая тишина), `pipewiresrc` / `pipewiresink` (гарнитура), `input-selector` и `output-selector` (или матричный `audiomixer`), подключёнными к `rtpbin` каждого вызова.
  - Переключение гарнитуры — смена свойства `active-pad` на селекторе на лету, без остановки пайплайна.
- **Сильные стороны:**
  - Абсолютная гибкость медиачасти на Linux: любые генераторы тонов, запись, визуализация уровня сигнала (волюметры прямо на карточках!), выбор любых устройств PipeWire.
  - Лицензия LGPL.
- **Слабые стороны:**
  - **Придётся вручную женить SIP/SDP и GStreamer:** самим парсить SDP-ответы от ВАТС, выбирать кодек, открывать локальные UDP-порты, передавать их в `udpsrc`/`udpsink` GStreamer, обрабатывать DTMF (RFC 4733) и смену портов при `re-INVITE`. По сути — написать половину собственного софтфона.

### Вариант 8. Go (`diago` / `sipgo`) + Wails (Web UI) + встроенный аудиокоммутатор на Go (`malgo`)

Развитие чистого Go-варианта с учётом требования по аудио. Библиотека **`diago`** (надстройка над `sipgo` от того же автора) уже умеет работать как SIP B2BUA/клиент с медиапотоками, генерацией тишины и воспроизведением аудио в RTP. Для вывода в локальную гарнитуру подключается `malgo` (обёртка над single-header C-библиотекой `miniaudio`, работает с PulseAudio/PipeWire/ALSA без внешних зависимостей).

- **Как работает переключение аудио:**
  - Каждая активная сессия `diago` читает/пишет PCM-фреймы (8 кГц, 20 мс).
  - В Go пишется простой потокобезопасный коммутатор на ~150 строк: по умолчанию все сессии читают нулевые буферы (тишину), а выбранная пользователем `activeCallID` обменивается PCM-буферами с открытым потоком `malgo` (микрофон/наушники).
- **Сильные стороны:**
  - Всё ещё **один компактный бинарник** под Linux, лицензия MIT.
  - Полный контроль над SIP-пакетами и заголовками (`Diversion`, `History-Info`, сырой SIP-лог в UI).
  - Никаких проблем с авто-Hold — логика переключения PCM-потоков полностью в наших руках.
- **Слабые стороны:**
  - В отличие от PJSIP или WebRTC (Janus), в `miniaudio` нет готового акустического эхоподавления (AEC) и продвинутого джиттер-буфера (при работе в гарнитуре/наушниках AEC не критичен, но на громкой связи ноутбука будет эхо; а базовый буфер и G.711 `diago` берёт на себя).
  - Поддержка только базовых кодеков из коробки (PCMU/PCMA, Opus через cgo), без экзотики вроде G.729.

## Итоговый шорт-лист (топ-3 под задачу с переключаемым аудио)

С учётом того, что локальную коммутацию гарнитуры между учётками нужно заложить в фундамент сразу:

1. **Фаворит из мира медиадвижков с SIP-плагинами: Вариант 4 — Janus (`libjanus_sip`) + Tauri (Web UI).**
   - Почему: не нужно писать ни строчки на C/C++ и не нужно изобретать SIP/SDP/аудиостек. За SIP отвечает матёрый Sofia-SIP внутри `janus_sip`, за звук, выбор USB-гарнитуры и бесшовное переключение микрофона/наушников между карточками отвечает штатный WebRTC / Web Audio API в окне приложения. UI (карточки, журналы, будущий таймлайн маршрута) верстается быстро и красиво.
2. **Фаворит из монолитных телефонных движков: Вариант 1 или 2 — PJSIP (`pjsua2`) + Qt6 / Tauri.**
   - Почему: встроенная матрица `pjmedia_conf` создана ровно для такой коммутации портов (гарнитура ↔ любой звонок, генератор тишины/тона ↔ остальные звонки). Нет локального проксирования WebRTC↔SIP, минимальное потребление ресурсов, эталонное поведение настоящего аппаратного SIP-телефона. Выбор между Python+Qt (быстрее старт) и C++/Rust+Tauri/Qt (проще распространять бинарник и нет SWIG).
3. **Фаворит по простоте поставки и контролю над SIP: Вариант 8 — Go (`diago`/`sipgo`) + Wails + `malgo`.**
   - Почему: единый независимый бинарник под Linux, идеальная прозрачность всех SIP-заголовков для построения цепочек переадресации на этапе 2 и простой собственный PCM-переключатель для гарнитуры (при условии, что достаточно стандартных кодеков G.711/Opus и работы в гарнитуре без сложного эхоподавления).
